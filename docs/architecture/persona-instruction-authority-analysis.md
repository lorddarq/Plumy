# Persona instruction authority: why Codex "takes on a more nuanced shape" and Claude doesn't

Status: research finding, not yet an accepted contract change
Date: 2026-08-18
Method: two parallel primary-source investigations — one against this codebase (`electron/services/agent-runtime-protocol-client.cjs`, `electron/domain/agent-runtime-context-pack.cjs`, `electron/domain/person-context-service.cjs`, `electron/services/workspace-service.cjs`, `docs/agentic/agent-instructions.md`), one against Anthropic's and OpenAI's own published documentation (Model Spec, Codex app-server protocol docs, Claude's Constitution, Claude Code Agent SDK docs, both companies' prompt-injection research).

## The question

A person's `agentInstructions`/`agentOperationalInstructions` fields (edited via `AgentInstructionFields.tsx`, defined as workspace "persona" context) visibly reshape Codex's behavior on a task. The same fields don't visibly reshape Claude's behavior the same way — Claude treats them as a strong recommendation, not something that overrides its own baked-in behavior. The working hypothesis going in was that this is a fundamental Anthropic-side design choice — Claude resists application-supplied instructions more than Codex does, as a deliberate prompt-injection defense.

## Bottom line

**That hypothesis is not supported by either provider's documentation, and the actual cause is a delivery gap in this codebase that applies to both providers, not a Claude-specific one.**

1. Both companies document a real, named, bounded-but-genuine authority tier for application/developer-supplied instructions — OpenAI's "Developer" tier, Anthropic's "Operator" tier. Anthropic's own Constitution states operators can "adjust," "expand," and "restrict" Claude's default behavior, using an explicit employer/employee trust analogy. Anthropic's documented prompt-injection defenses are scoped to *attacker-supplied content the agent encounters mid-task* (a poisoned webpage, a malicious tool result) — not to the operator's own system prompt. Nothing in Anthropic's published research frames resisting the calling application's instructions as a safety property.
2. **Omvra never uses the privileged channel for either provider.** Persona/instruction content never reaches the per-turn runtime protocol for Codex, Claude, or generic ACP — all three clients in `agent-runtime-protocol-client.cjs` send exactly one thing per turn, a plain-text "user"/"input" block built from `agent-runtime-context-pack.cjs`, which is purely task-shaped (title/description/status/context-ledger entries) and has no `agentInstructions` field at all. Persona content is exposed *only* as MCP tool-call/resource data (`agent.resolve_task_context`), which the agent must proactively decide to fetch — identical mechanism, identical wording, for every provider.
3. Both providers document exactly the privileged channel Omvra isn't using: Codex's app-server protocol has `settings.developer_instructions` (additive) and config's `model_instructions_file` (full replace of built-in instructions) — described in Codex's own docs as parallel, equally-supported options. Claude Code has `--append-system-prompt` (additive) and `--system-prompt` (full replace) with the identical additive/substitutive shape. Omvra constructs neither flag anywhere in `electron/`, for either provider (confirmed by repo-wide grep).
4. The one genuinely provider-differential fact found, and it cuts in the opposite direction from "Omvra treats Claude worse": Anthropic's own SDK docs state plainly that content positioned in a **system prompt** carries more weight than the same content positioned in a **user-turn/conversation-context** message — and that CLAUDE.md (Claude's AGENTS.md analogue) is deliberately injected as conversation context, "not into the system prompt," specifically *because* of this weight difference. Codex's AGENTS.md, by contrast, is unconditionally read "before doing any work" and concatenated directly into Codex's own instruction chain, with no documented lower-weight channel. So even where a real asymmetry exists, it's about how each provider's *own native file convention* is weighted — and Omvra writes neither `AGENTS.md` nor `CLAUDE.md` for either provider, so this asymmetry isn't currently in play either.

**In short: the contracts don't have a structural gap that favors one provider's model over the other's. Omvra's delivery mechanism has a structural gap that under-uses the privileged channel for both providers equally — and happens to produce a visible difference in practice only because of a separate, unrelated code asymmetry (below), not because of anything about how Claude is designed.**

## The separate asymmetry that likely actually explains the observed difference

While tracing MCP wiring, the codebase investigation found: `electron/services/agent-runtime-session-runner.cjs`'s `clientOptions()` (lines 92–107) issues a scoped, bearer-token-authenticated MCP grant — the mechanism that makes `agent.resolve_task_context` (and therefore persona data) reachable at all — **only when `integrationMode === 'claude-stream-json-stdio'`**. Both production call sites of `startSession()` (lines 579, 643) pass no MCP configuration for Codex or generic ACP. `CodexAppServerClient.startSession()`'s signature doesn't even accept an MCP parameter.

This means it is currently unresolved from the code alone whether a Codex session launched through Omvra has *any* live path to Omvra's `agent.resolve_task_context` tool at all in this flow. If it doesn't, any Codex persona-following the user observes cannot be coming from Omvra's contract at all — it would have to come from something entirely outside this app: a user-maintained, statically-configured `~/.codex/config.toml` MCP entry, or (more likely, per the finding above) Codex's own native `AGENTS.md` discovery picking up unrelated project-level guidance, independent of anything Omvra constructs.

This also appears to contradict this repo's own stated design principle in `docs/architecture/acp-runtime-session-lifecycle-contract.md:284-294` ("Omvra must not pass `mcp_servers`, `mcpServers`, `--mcp-config`, provider CLI overrides... as part of task execution") — the Claude-only grant flow (landed in the recent `5d6f3b9 fix: authenticate Claude MCP sessions and report startup status` commit) does exactly what that doc says not to do, for Claude only. Whether that doc is stale or the Claude branch is an unreviewed exception isn't resolved here — flagging it as a real, separate finding.

## What the primary sources actually say

### OpenAI / Codex

- Model Spec (`model-spec.openai.com`, fetched Dec 2025 revision): hierarchy `Root → System → Developer → User → Guideline`. Developer tier: *"Instructions given by developers using our API. Models should obey developer instructions unless overridden by root or system instructions,"* and has "greater authority" than User when both are present.
- Foundational instruction-hierarchy paper (Wallace et al., arXiv:2404.13208, OpenAI-authored): the whole research program's stated premise is to make "system prompts (e.g., text from an application developer)" **more** trusted relative to untrusted user/third-party text — the opposite threat model from "resist the app."
- Codex app-server protocol (`github.com/openai/codex/codex-rs/app-server/README.md`, the exact protocol Omvra speaks via `codex app-server --stdio`): `settings.developer_instructions: null` means "use built-in instructions"; the same doc frames providing "their own instructions explicitly" as a co-equal alternative, not a lesser one. Config reference (`developers.openai.com/codex/config-file/config-reference`) separately documents `model_instructions_file`: *"Replacement for built-in instructions instead of AGENTS.md."*
- `AGENTS.md`: *"Codex reads AGENTS.md files before doing any work,"* concatenated root-to-cwd, closer files overriding farther ones by position in the combined prompt.

### Anthropic / Claude

- Claude's Constitution (`anthropic.com/constitution`): principal hierarchy Anthropic → Operator → User, explicitly *"not a strict hierarchy."* Operators (the tier a host application occupies): *"can adjust Claude's default behavior for users,"* *"can... expand or restrict Claude's default behaviors,"* and Claude is told to treat operator messages *"like messages from a relatively (but not unconditionally) trusted manager or employer."*
- Prompt-injection research (`anthropic.com/research/prompt-injection-defenses`, Nov 24 2025) and the Claude Opus 4.5 System Card (same date, §5.2): the documented threat model is explicitly about protecting *"the original user intent"* from attacker-supplied content encountered mid-task (a poisoned webpage, a malicious tool result) — *"the attacker's goal is to hijack the agentic loop."* No passage in either source frames resisting operator/developer-authored system-prompt content as part of this defense.
- Claude Code Agent SDK docs (`code.claude.com/docs/en/agent-sdk/modifying-system-prompts`): `--append-system-prompt` / `systemPrompt: {preset, append}` — additive, preserves built-in tools/safety. `--system-prompt` / custom `systemPrompt` string — full replace, *"Complete control,"* but *"Built-in safety: Must be added."* Structurally identical additive/substitutive shape to Codex's `developer_instructions`/`model_instructions_file`.
- The one directly load-bearing quote for the user's original hypothesis: *"CLAUDE.md doesn't change the system prompt itself: the SDK injects its content into the conversation as project context, not into the system prompt... Instructions in the user message carry marginally less weight than the same text in the system prompt."* This is Anthropic documenting a real positional-authority gradient — but scoped to conversation-context-positioned content (CLAUDE.md, and by the same logic, Omvra's MCP-fetched persona data) versus system-prompt-positioned content. It is not a statement that Claude discounts *operator system-prompt* content.

## What this means for Omvra, if the goal is parity

Not prescribing a change here — this is a research finding, and `docs/agentic/agent-instructions.md`'s existing trust-boundary framing (persona is advisory, never above client/system/developer/tool/security/task-acceptance instructions) is a deliberate, considered design choice that a fix would need to respect, not override. But if the goal is "Claude and Codex should be equally capable of having persona content meaningfully shape their behavior, within that same non-authoritative bound," the concrete, documented levers both providers already expose and Omvra doesn't yet use are:

- For Claude: `--append-system-prompt` (`electron/services/agent-runtime-protocol-client.cjs`'s `ClaudeStreamJsonClient.startSession()`, where the `args` array is built) would move persona content from the lowest-weight channel available (MCP-fetched, several inferential steps removed from anything Claude directly reasons over) to the channel Anthropic's own docs say carries more weight than user-turn content.
- For Codex: `settings.developer_instructions` on `turn/start` (`CodexAppServerClient`) would move it into the same tier `AGENTS.md` already occupies natively, rather than leaving it to whatever MCP access a Codex session happens to have — which, per the finding above, may currently be none at all through this runner.
- Separately and first: resolve whether Codex/generic-ACP sessions are supposed to receive MCP wiring at all (the `clientOptions()` asymmetry and the apparent doc/code contradiction in `acp-runtime-session-lifecycle-contract.md`), since that's a correctness question independent of the persona question and affects whether `agent.resolve_task_context` is even reachable for non-Claude runtimes today.
